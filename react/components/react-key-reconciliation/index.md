## Что такое согласование (reconciliation)

Каждый раз, когда состояние или пропсы компонента изменяются, React вызывает функцию рендера и получает новое дерево React-элементов. Чтобы обновить реальный DOM эффективно, React не перестраивает его с нуля — вместо этого он сравнивает новое дерево элементов со старым и вычисляет минимальный набор операций, необходимых для приведения DOM в актуальное состояние. Этот процесс называется **согласованием** (reconciliation).

Алгоритм согласования опирается на два ключевых допущения:

1. Два элемента с разными типами (например, `<div>` и `<span>`) всегда порождают разные деревья — старое дерево уничтожается, новое создаётся с нуля.
2. Элементы одного типа, которые рендерятся в одной позиции, считаются «одним и тем же» компонентом — React обновляет его пропсы, не пересоздавая экземпляр.

Именно второе допущение и создаёт проблему при работе со списками.

## Проблема со списками

Рассмотрим простой список:

```jsx
<ul>
  <li>Молоко</li>
  <li>Хлеб</li>
</ul>
```

Если добавить элемент **в конец**, React сравнит первые два `<li>` и обнаружит, что они не изменились. Новый третий элемент будет вставлен — всё работает оптимально.

```jsx
<ul>
  <li>Молоко</li>
  <li>Хлеб</li>
  <li>Масло</li>  {/* добавлен в конец */}
</ul>
```

Но если добавить элемент **в начало**, ситуация меняется кардинально:

```jsx
<ul>
  <li>Масло</li>  {/* добавлен в начало */}
  <li>Молоко</li>
  <li>Хлеб</li>
</ul>
```

React сравнивает элементы попозиционно. Первый `<li>` в новом дереве содержит «Масло», а в старом — «Молоко». React видит два разных текстовых узла и обновляет все три `<li>`. Вместо одной операции вставки получается три операции обновления — это неэффективно и может привести к сбросу состояния дочерних компонентов.

## Как key решает эту проблему

Атрибут `key` позволяет React однозначно идентифицировать каждый элемент в списке. Вместо сравнения по позиции React сравнивает элементы **по ключу**.

```jsx
<ul>
  <li key="butter">Масло</li>
  <li key="milk">Молоко</li>
  <li key="bread">Хлеб</li>
</ul>
```

Теперь при добавлении «Масла» в начало React видит:
- `key="butter"` — новый, нужно создать
- `key="milk"` — уже существует, переместить
- `key="bread"` — уже существует, переместить

Одна операция создания + перестановки вместо трёх обновлений. Состояние компонентов `milk` и `bread` при этом сохраняется.

## Ключи и сохранение состояния

Самое важное последствие работы ключей — управление жизненным циклом компонентов. Когда React видит элемент с тем же ключом, он сохраняет его экземпляр и обновляет только пропсы. Когда ключ изменяется или исчезает, компонент **размонтируется** и создаётся новый.

Рассмотрим пример с полем ввода:

```jsx
function TodoItem({ todo }) {
  const [draft, setDraft] = useState(todo.text);

  return (
    <input
      value={draft}
      onChange={e => setDraft(e.target.value)}
    />
  );
}

function TodoList({ todos }) {
  return (
    <ul>
      {todos.map(todo => (
        <TodoItem key={todo.id} todo={todo} />
      ))}
    </ul>
  );
}
```

Если пользователь редактирует черновик в поле ввода, а затем список перестраивается (например, задачи сортируются), локальное состояние `draft` каждого `TodoItem` останется нетронутым — благодаря стабильным ключам `todo.id`.

Если убрать `key` или использовать индекс массива, перестановка задач приведёт к тому, что черновики «перепутаются» между строками.

## Типичная ошибка: key={index}

Использование индекса массива в качестве ключа — самая распространённая ошибка при работе со списками.

```jsx
// Плохо
{todos.map((todo, index) => (
  <TodoItem key={index} todo={todo} />
))}
```

Почему это опасно: индекс привязан к позиции, а не к данным. Если список изменяется (добавление в начало, удаление, сортировка), индексы перераспределяются. React считает, что элемент с `key={0}` «тот же самый», хотя реально в этой позиции теперь другие данные.

Последствия:
- Локальное состояние компонентов «прилипает» к позиции, а не к данным
- Анимации и CSS-переходы срабатывают неправильно
- Поля форм показывают устаревшие значения
- Возможны трудноуловимые баги при удалении элементов из середины списка

```jsx
function BugDemo() {
  const [items, setItems] = useState([
    { id: 1, text: 'Первый' },
    { id: 2, text: 'Второй' },
  ]);

  const addToStart = () => {
    setItems([{ id: Date.now(), text: 'Новый' }, ...items]);
  };

  return (
    <div>
      <button onClick={addToStart}>Добавить в начало</button>
      <ul>
        {items.map((item, index) => (
          // key={index} — баг: состояние input привяжется к позиции
          <li key={index}>
            {item.text}: <input defaultValue={item.text} />
          </li>
        ))}
      </ul>
    </div>
  );
}
```

После нажатия кнопки новый элемент появится в начале, но содержимое `<input>` останется на своих позициях — пользователь увидит, как текст в полях «съехал» вниз.

## Когда индекс допустим в качестве ключа

Индекс как ключ приемлем только при одновременном выполнении трёх условий:

1. Список **статичен** и никогда не будет переупорядочен
2. Элементы списка **не имеют идентификаторов**
3. Список **не фильтруется** и не пересчитывается

Пример подходящего случая — статичный список пунктов документации, который отрисовывается один раз и больше не изменяется:

```jsx
const STEPS = ['Установка', 'Настройка', 'Запуск'];

function Guide() {
  return (
    <ol>
      {STEPS.map((step, index) => (
        <li key={index}>{step}</li>  {/* допустимо: список никогда не меняется */
      ))}
    </ol>
  );
}
```

## Правила хороших ключей

**Стабильность.** Ключ должен оставаться одним и тем же при повторных рендерах. Не генерируйте ключи случайно:

```jsx
// Плохо — новый ключ при каждом рендере, компонент будет пересоздаваться
<Item key={Math.random()} />

// Плохо — то же самое
<Item key={uuid()} />
```

**Уникальность в пределах списка.** Ключи должны быть уникальны среди **братских** элементов, но не обязаны быть глобально уникальными.

```jsx
// Допустимо: одинаковые ключи в разных списках не конфликтуют
function Page() {
  return (
    <>
      <ul>
        {posts.map(p => <li key={p.id}>{p.title}</li>)}
      </ul>
      <ul>
        {comments.map(c => <li key={c.id}>{c.text}</li>)}
      </ul>
    </>
  );
}
```

**Предсказуемость.** Ключ должен однозначно идентифицировать сущность. Используйте:
- ID из базы данных
- Уникальный slug или code
- Составной ключ, если одного поля недостаточно: `key={${category}-${id}}`

## Ключи за пределами списков

key — это не только инструмент для списков. Его можно использовать для **принудительного сброса состояния** любого компонента.

Предположим, есть форма редактирования пользователя. При переключении между пользователями нужно сбросить все поля формы к новым значениям:

```jsx
function UserEditor({ userId }) {
  return <UserForm key={userId} userId={userId} />;
}

function UserForm({ userId }) {
  const [name, setName] = useState('');
  const [email, setEmail] = useState('');

  useEffect(() => {
    fetchUser(userId).then(user => {
      setName(user.name);
      setEmail(user.email);
    });
  }, [userId]);

  return (
    <form>
      <input value={name} onChange={e => setName(e.target.value)} />
      <input value={email} onChange={e => setEmail(e.target.value)} />
    </form>
  );
}
```

Без `key={userId}` при смене пользователя компонент `UserForm` переиспользуется, и до завершения запроса в полях будут видны данные предыдущего пользователя. С `key={userId}` React размонтирует старый экземпляр и смонтирует новый — форма всегда начинает с чистого состояния.

Это гораздо чище, чем добавлять `userId` в зависимости `useEffect` и вручную сбрасывать каждое поле.

## Ключи и React DevTools

При разработке React DevTools показывает ключи рядом с именами компонентов в дереве. Это удобно для диагностики: если ключи нестабильны или дублируются, вы сразу это увидите.

Tакже React выводит предупреждение в консоль при отсутствии ключей:

```
Warning: Each child in a list should have a unique "key" prop.
```

Никогда не игнорируйте это предупреждение — оно сигнализирует о потенциальных проблемах с производительностью и корректностью работы.

## Итог

Атрибут `key` — это подсказка React о том, как сопоставлять элементы между рендерами:

- Одинаковый ключ = тот же компонент, обновить пропсы
- Изменился или исчез ключ = размонтировать старый, создать новый

Основ использования ключей три:
1. Всегда добавляйте `key` при рендере списков
2. Используйте стабильные уникальные идентификаторы из данных, а не индексы или случайные значения
3. Используйте `key` для намеренного сброса состояния компонента при смене контекста

Правильное понимание ключей и reconciliation — фундамент для написания предсказуемых React-компонентов без скрытых багов с состоянием.
